# Hover Latency — Journal

## 2026-10-20 — Desk opened
- **Purpose:** Find and fix the hover-latency regression the operator sees in game — hovering a unit sometimes shows the tooltip immediately and sometimes takes a very long time. 0.8.3 was fast; the 0.8.4 tree is not. Release blocker.
- **Scope:** `Libs/LibForeverInspector/LibForeverInspector.lua`, `main.lua`, `Tests/harness/detect_test.lua`, `Tests/harness/tooltip_test.lua`. NOT `gearscore.lua`, NOT `options.lua`, NOT `TacoTip_Extras/**`.
- **Symptom (operator, verbatim):** "sometimes it when i hover it shows up right away other times it takes forever. it was fast before, now its buggy mess." Earlier: running the scan control left the tooltip showing no scores until he reloaded.
- **Leading suspect (a lead, not a conclusion):** 0.8.4's proximity scan (`TacoTipConfig.scan`, default on) issues inspect requests through the SAME single-slot inspect pipeline the hover uses, so the hovered unit's own inspect waits behind scan requests.
- **Prior art read:** `bench/audits/2026-10-20-session-retrospective.md`, `bench/audits/2026-10-20-inspect-and-guild-line-history.md`, `desks/scan-crash/journal.md` (the scan-crash lane already landed pending-slot-release guards and the `Core.RequestLocalScan` fix).
- **Next step:** read `LibForeverInspector`'s inspect pipeline (queue tick, pending slot, priority), then build a harness case that measures hover latency with scan ON vs OFF on all five client profiles.

## 2026-10-20 — The cause is measured, not guessed
- **Method:** a scratch driver under `/tmp/opencode/hoverlat/` drives the REAL `LibForeverInspector` through a simulated client frame loop (events before the tickers' OnUpdate, the library's 0.5s queue ticker and 2.0s scan ticker, a modelled server round trip, "mouseover" existing only while the cursor is over a unit). Metric: seconds from the hover to the hovered unit's cache entry (the moment main.lua's INVENTORY_READY handler re-renders the tooltip with scores).
- **VERIFIED — the scan is the cause.** With the scan ON the hover latency is bimodal (the fast case = one round trip, the slow case = two round trips + the pacing window + up to 0.5s of tick quantisation); with the scan OFF it is exactly one round trip on every client. Single-hover sweep, Classic Era: scan OFF 0.20/0.50/1.00/2.00s (round trips 0.2/0.5/1.0/2.0) vs scan ON max 1.45/1.75/1.80/3.75s. Hover-sequence sweep (gap 1.5s), Classic Era: scan OFF 0.20/0.50/1.00 vs scan ON max 0.70/1.00/2.00. Same shape on all five clients.
- **VERIFIED — the mechanism, in the library:** (1) the scan's `DoInspect` DISPATCHES on the spot when the pending slot is free, so it takes the single pending slot away from the hovered unit; (2) that request also opens the global pacing window (`nextInspectTime = now + INSPECT_DELAY`, 1.0s on the Classic family, 0.4s on the modern pair) and the hovered unit is QUEUED rather than dispatched while it is open; (3) the queue is drained NEWEST-FIRST (`for i = #queue, 1, -1`), so a scan candidate queued after the hover is served first; (4) the hovered unit has NO priority in `inspectQueueTick` — only the TARGET has one (Priority 1).
- **REFUTED — the queue-order starvation alone is not the main cost:** adding only the hovered-unit priority arm changes nothing measurable (the hovered unit is usually the newest queue entry).
- **Next step:** land the fix and pin it.

## 2026-10-20 — Landed: the hovered unit owns the inspect pipeline
- **Changed (library only, `Libs/LibForeverInspector/LibForeverInspector.lua`):**
  1. the queue tick's new **Priority 1 is the unit under the cursor** (before the target, before the queue) — the hovered unit used to be just another queue entry and the queue is drained newest-first, so a scan candidate queued after the hover was served first;
  2. **the hovered unit is not held back by a pacing window another unit opened** (in `DoInspect` and in the tick's gate) — that window (`INSPECT_DELAY`) is the anti-re-request throttle for the same render pass, not a delay for a fresh hover;
  3. **the proximity scan stands down while the hovered unit is waiting**: its candidate is queued instead of dispatched on the spot, so the scan cannot take the single pending inspect slot away from the unit in front of the player. With nothing waiting the scan asks exactly as it always did (that request is what teaches the client its real inspect range — the existing `detect_test` pins for the refused-scan learning still pass).
- **Not changed:** `gearscore.lua`, the range gate (`NEARBY_ASK_YARDS`, `INSPECT_INTERACT_DISTANCE_INDEX`, the probe guard, the learned ceiling), every timing constant (`INSPECT_DELAY`, `INSPECT_PENDING_TIMEOUT`, the 0.5s queue ticker, the 2.0s scan ticker, `CACHE_REFRESH_DELAY`, `INSPECT_REJECT_COOLDOWN`), the scoring formula, `main.lua`, `options.lua`, `TacoTip_Extras/**`, the locale files, the `.toc` files.
- **Measured after (harness driver, hover latency in seconds, worst of a 40-point sweep of the hover moment, scan ON):** Classic Era / TBC / Titanforge — round trip 0.2s: 1.45 → **0.20** (scan OFF baseline 0.20); 0.5s: 1.75 → **0.75** (baseline 0.50); 1.0s: 1.80 → **1.75** (baseline 1.00); 2.0s: 3.75 → **3.75** (baseline 2.00). WoW Forever / Retail — 0.2s: 0.45 → **0.20**; 0.5s: 0.75 → **0.75**; 1.0s: 1.75 → **1.75**; 2.0s: 3.75 → **3.75**. Hover SEQUENCE (the cursor sweeping a group, 1.5s apart): classic 0.2s 0.70 → **0.20**, 0.5s 1.00 → **0.50**, 1.0s 2.00 → **2.00**.
- **Residual, stated honestly:** a scan request that is ALREADY IN FLIGHT when the cursor arrives still costs the hovered unit one round trip (the client inspects one unit at a time, and the library models that with a single pending slot). Removing that would mean abandoning an in-flight server request, which would change the refusal/pending attribution machinery 0.8.3's range fix depends on — not done in this lane.
- **Pins:** `Tests/harness/detect_test.lua`, five new checks on all five clients (the scan does not take the slot; the hovered unit is dispatched before a queued scan candidate; the hovered unit is not held back by a pacing window; with the scan ON the hovered unit's data lands in one round trip; the scan still asks for its candidate when nothing is waiting).
- **Revert-to-fail proofs** (copies under `/tmp/opencode/hoverlat/proof`, driver `/tmp/opencode/hoverlat/revert_proof.py`): R1 (the hovered-unit priority arm) → 15 red lines; R2 (the pacing-window bypass) → 5 red lines; R3 (the scan stands down) → 10 red lines; all three reverted → 20 red lines.
