## 2026-10-20 — Investigation so far (read-only)
- **Library, `INSPECT_READY` handler** (`Libs/LibForeverInspector/LibForeverInspector.lua:3846-3921`): `cacheUnitData(unit, guid)` at `:3884` runs BEFORE the pending-slot release at `:3897-3900`. `cacheUnitData` ends at `:3802-3803` with `lib.callbacks:Fire("INVENTORY_READY", ...)` / `Fire("TALENTS_READY", ...)`. So ANY raise inside `cacheUnitData` leaks the pending slot.
- **`cacheUnitData` has unguarded client calls of its own** (not just the consumer callbacks): `:3774 getModernSpecData`, `:3781 buildGroupTalentPoints`, `:3782 buildSpecIndexByGroup`, `:3783 GetActiveSpecGroupFor`, and on the classic family `:3787-3789` the same three. These are NOT pcall-guarded, so a raise there leaks the slot with no consumer involved at all.
- **The bundled `CallbackHandler-1.0` (v7) dispatches with `xpcall(method, errorhandler, ...)`** (`Libs/CallbackHandler-1.0/CallbackHandler-1.0.lua:27-34`). In game `geterrorhandler()(err)` DISPLAYS the error and returns, so a consumer raise is displayed but does not propagate; in the harness `geterrorhandler` is absent, so the fallback is `error` and it DOES re-raise. The leak is therefore harness-provable and in-game-provable through the library's own unguarded calls.
- **The pending slot is not permanently wedged by one leak**: the 0.5s queue tick's watchdog (`:5192-5213`) releases a pending slot older than `INSPECT_PENDING_TIMEOUT` — but ONLY when `inspectPendingSince > 0`, so a slot taken with a zero/absent timestamp never ages out.
- **Extras, remote capture path** (`TacoTip_Extras/Scanner.lua:1004-1094`): `capturePlayerCells` `:1019`, `Cache.SetPending` `:1061`, `Scoring.Evaluate` `:1076`, `Cache.PublishComplete` `:1083`, `queueRankSync` `:1091` are unguarded at the call site; `captureSlot` `:1030` is individually pcall-guarded.
- **Empirical result:** the harness's remote-capture fixture (one item, slot 1) and a NEW full-16-item remote fixture under the TBC profile BOTH complete without raising (`cache state=complete`, `gearScore=2131`). So the raise is NOT in the happy path — it needs a client shape the harness does not build.

## 2026-10-20 — The measurement that changed the picture
- **A consumer callback's raise CANNOT reach the library.** The bundled `CallbackHandler-1.0` v7 dispatches every handler under `xpcall(method, errorhandler, ...)` and **discards the result** (`Libs/CallbackHandler-1.0/CallbackHandler-1.0.lua:27-34`). Measured on lua5.1/lua5.4/luajit: an error raised *inside* an xpcall error handler is returned as the xpcall's result ("error in error handling"), NOT propagated. In game `geterrorhandler()(err)` displays the error and returns normally. So the consumer's raise is swallowed by the dispatch on every client: `cacheUnitData` always completes and the pending slot is always released. **The brief's premise that a consumer-callback raise aborts `cacheUnitData` is not reproducible.**
- **What IS reproducible:** a raise in the cache step's OWN client reads. Every read there is pcall-guarded internally except one — `uptimeSeconds()` (the first line of `cacheUnitData`) calls `GetTime()` bare. A raise there aborts the handler before the release and leaks the pending slot. That is the hole the pin now covers, injected through the real code path.
- **The Extras' capture path fuzzed** (33 remote shapes + 21 local shapes, TBC profile, copy under /tmp/opencode): the unguarded client calls are `UnitClass` and `UnitLevel` (via `capturePlayerCells`), `GetServerTime` (via `queueRankSync`) and `GetInventoryItemID`/`GetInventoryItemLink` (via `captureSlot`, guarded in the remote path but NOT in the local path). Every other client call in those paths already degrades instead of raising; these were the outliers.
- **The scan control:** `RankBrowser.StartScan` called `scanner.BeginGeneration("leaderboard")` and never `RunGeneration`, so the scanner was left "pending" with nothing capturing it — and it STOLE a scan that was already scheduled (the scheduled run carried the older generation, `RunGeneration` refused it). The Extras never calls any library inspect/scan API (grep), so the control that wedges the shared engine is the MAIN add-on's "Scan nearby players" (the only thing that makes the library inspect); the leaderboard button is a second, independent defect.
